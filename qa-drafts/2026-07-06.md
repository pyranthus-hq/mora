### 1. [P1][concurrency][reliability] `mora write` under concurrent load silently loses index entries — root cause: full reindex on every write races with concurrent writers

**Labels:** bug, concurrency, reliability, P1
**id:** `concurrency-index-loss` (baseline, reproduced — reported here per first-run capture)

**Summary**
Launching 25 concurrent `mora write` calls into the same scope produces 25 files on disk but only 10 of them are found via `mora search` immediately afterward. A `mora index rebuild` recovers all 25. No write command reported an error — every `mora write` returned exit 0 with a valid `"id"` in its JSON output — so a caller has no signal that its memory silently failed to become searchable.

**Impact**
For an agent driving Mora as memory (the primary use case), a burst of writes — e.g. an agent ingesting several emails/notes in a tight loop — can silently drop up to ~60% of them from the index in this reproduction, with zero error surfaced. The data is not lost (the markdown file is safely on disk), but it is unsearchable and effectively invisible to `mora search`/`mora think` until someone thinks to run `index rebuild`. This is exactly the kind of "trust the tool captured it" failure that's most damaging for a memory system.

**Root cause (found in code)**
`cmdWrite` (internal/mora/mora.go:879) calls `rebuildIndex(ctx, cfg)` after writing the memory file — this is a *full* reindex (`DELETE FROM memories` + rescan `allMemoryFiles(cfg)` + reinsert, all in one transaction, see `rebuildIndexWithPolicy` at internal/mora/mora.go:3352). There is no incremental single-row insert path for `write`. When N processes write concurrently, each one lists all memory files, then commits a full DELETE+reinsert. A rebuild that lists files before a slower sibling process has finished writing its file will not see that file, and if its commit lands last, it wins — erasing that sibling's index row even though the underlying `.md` file exists on disk. `_txlock=immediate` + `busy_timeout(15000)` correctly serializes the *transactions*, but does nothing to prevent this lost-update race between file-listing and commit order.

**Reproduction**
```bash
export HOME=/tmp/moraqa
for i in $(seq 1 25); do
  mora write --scope concur --title "Concur $i" --text "concurtoken_xyz_$i" --json &
done
wait
ls vault/memories/concur/ | wc -l                       # 25
mora search concurtoken_xyz --limit 40 --json | python3 -c "import json,sys;print(len(json.load(sys.stdin)))"   # 10 (< 25)
mora index rebuild
mora search concurtoken_xyz --limit 40 --json | python3 -c "import json,sys;print(len(json.load(sys.stdin)))"   # 25 (recovered)
```

**Expected vs Actual**
- Expected: every successful `mora write` is searchable immediately after it returns, regardless of concurrent writers.
- Actual: under concurrency, a full-rebuild-per-write pattern loses rows for other concurrently-written memories; no error is surfaced.

**Suggested fix**
Replace the full-rebuild-on-write with an incremental insert/upsert of just the new memory's row (single `INSERT OR REPLACE` into `memories`/`memories_fts` inside its own `_txlock=immediate` transaction), reserving the full `rebuildIndex` path for `mora index rebuild`/explicit repair. This removes the file-listing race entirely and makes each write's cost O(1) instead of O(vault size).

**Environment:** Linux 6.18.5 x86_64, go1.25.8, mora dev (commit db3958f)

### 2. [P1][security] `--scope` accepts path-traversal segments and writes outside the vault root

**Labels:** bug, security, P1
**id:** `scope-path-traversal` (baseline, reproduced)

**Summary**
`mora write --scope '../../escaped' --title E --text X` succeeds and writes the memory file to `/tmp/moraqa/escaped/mem_....md` — one level above the vault directory (`/tmp/moraqa/vault/`) — rather than being rejected or sanitized.

**Impact**
A vault is supposed to be the trust boundary for a local-first memory store (single directory a user backs up / syncs / shares). Any code path that accepts a scope string from an agent, a plugin, or an MCP tool call can write arbitrary files outside that boundary using `..` segments, which is a real path-traversal vulnerability — worse if `mora mcp serve` exposes `write` to an untrusted or semi-trusted agent that itself received attacker-influenced input (e.g. content pulled from an email/webpage feeding a "scope" field).

**Reproduction**
```bash
export HOME=/tmp/moraqa
mora write --scope '../../escaped' --title E --text X --json
# path in output: /tmp/moraqa/escaped/mem_....md  (OUTSIDE /tmp/moraqa/vault/)
find /tmp/moraqa -iname '*escaped*'   # confirms the dir was created outside the vault
```

**Expected vs Actual**
- Expected: `--scope` is validated/sanitized to a relative path confined to `<vault>/memories/`; a `..`-escaping scope is rejected with a clear error.
- Actual: the scope is joined directly into a filesystem path with no confinement check, allowing writes anywhere the process has permissions to reach.

**Suggested fix**
Resolve the target path with `filepath.Clean`/`filepath.Rel` against the vault's memories root and reject (don't silently sanitize) any scope whose resolved path escapes that root.

**Environment:** Linux 6.18.5 x86_64, go1.25.8, mora dev (commit db3958f)

### 3. [P2][dx] `--help` is broken for most top-level commands — raw flag errors leak, and `think --help` executes a real query

**Labels:** dx, P2
**id:** `dx-help-and-validation` (baseline, reproduced)

**Summary**
Only `mora search --help` behaves correctly (prints a usage line, exit 0). Every other command tested leaks Go's raw flag-parsing error, or worse:
- `mora init --help` → `flag: help requested` (exit 1)
- `mora write --help` → `flag: help requested` (exit 1)
- `mora context --help` → `flag: help requested` (exit 1)
- `mora think --help` → **treats `--help` as the literal query text** and runs a real (empty) evidence-gathering query, printing `Q: --help`, an evidence section, and a synthesis-prompt hint — no help text at all.

**Impact**
Any user or agent that runs the conventional `--help` to learn a command's flags gets either a cryptic internal error string or, for `think`, an actually-executed no-op query — neither tells them how to use the command. This is a first-touch DX failure and, for `think`, a "help should never have side effects / do real work" violation (harmless here since the query is empty, but it establishes the wrong contract for automation that might legitimately expect `--help` to be a no-op fast-path).

**Reproduction**
```bash
export HOME=/tmp/moraqa
mora init --help;    echo $?     # flag: help requested / 1
mora write --help;   echo $?     # flag: help requested / 1
mora context --help; echo $?     # flag: help requested / 1
mora think --help                # "Q: --help" + runs real evidence lookup
mora search --help;  echo $?     # usage: mora search <query> ... / 0   (correct, for comparison)
```

**Expected vs Actual**
- Expected: every command's `--help`/`-h` prints a usage message to stdout and exits 0, consistently, with no query execution.
- Actual: inconsistent across commands; several leak the underlying Go `flag` package error text, and `think` runs a live query against the vault.

**Suggested fix**
Standardize on one help path: intercept `-h`/`--help` before/within each subcommand's `flag.FlagSet` (as `search` already does) and print a fixed usage string, never falling through to Go's default flag-error text or to query execution.

**Environment:** Linux 6.18.5 x86_64, go1.25.8, mora dev (commit db3958f)

### 4. [P3][dx] `tasks add`/`tasks list` — flag-shaped names are accepted verbatim (silent garbage tasks), and `list` conflates done with live

**Labels:** dx, P3
**id:** `tasks-add-flag-as-literal-name` (net-new) and `tasks-list-returns-done` (baseline, reproduced)

**Summary — net-new (`tasks-add-flag-as-literal-name`)**
`mora tasks add` takes its name as the *first positional* argument (`internal/mora/mora.go:1279`, `name := strings.TrimSpace(args[1])`) with no check for whether that argument looks like a flag. `mora tasks add --title "QA Task Alpha"` does not error — there is no `--title` flag at all — it silently creates a live task literally named `--title` (exit 0, `task added: --title`). Likewise `mora tasks add --help` creates a task literally named `--help` instead of showing help (and, confusingly, exits 1 like a real error while still having written the row).

**Summary — baseline (`tasks-list-returns-done`)**
The package doc/comment at `internal/mora/mora.go:409` describes `mora tasks list --json` as returning "the current live tasks," but a task marked `done` via `mora tasks done <name>` remains in the same `tasks list --json` array (with `"status":"done"`) alongside queued tasks — there is no filtering, so "live tasks" is inaccurate and a consumer that doesn't check `status` will treat closed tasks as still open.

**Impact**
A user or agent typo (`--title` instead of the correct positional-name syntax) doesn't fail loudly — it silently pollutes `live-tasks.md` with a garbage row that looks like a real P1 task ("--title", "--help"), which is exactly the kind of noise a task list is supposed to prevent. Combined with `tasks list` never dropping done items, an agent consuming `tasks list --json` without carefully checking `status` will keep re-surfacing both garbage rows and already-completed work.

**Reproduction**
```bash
export HOME=/tmp/moraqa
mora tasks add --title "QA Task Alpha"; echo $?      # "task added: --title", exit 0 (should be a usage error)
mora tasks add --help                                # "task added: --help", but exit 1 (inconsistent + still creates data)
mora tasks list --json | python3 -m json.tool         # both garbage rows present

mora tasks add "Real Task"
mora tasks done "Real Task"
mora tasks list --json                                # "Real Task" still present with status:"done", mixed in with queued rows
```

**Expected vs Actual**
- Expected: `tasks add <flag-looking-string>` is rejected with the documented usage error (`usage: mora tasks add <name> ...`), not silently accepted as a name; `tasks list` (or a documented flag) returns only non-done rows to match its "live tasks" description.
- Actual: any string, including bare flags, is accepted as a task name with no validation; `list` returns all tasks regardless of status.

**Suggested fix**
In `tasks add`, reject a first positional that starts with `-`/`--` (point the user at the usage string) unless it's explicitly quoted content. For `list`, either filter `status != "done"` by default and add `--all` for the full history, or fix the doc comment to stop calling it "live tasks" if all statuses are intentionally included.

**Environment:** Linux 6.18.5 x86_64, go1.25.8, mora dev (commit db3958f)
